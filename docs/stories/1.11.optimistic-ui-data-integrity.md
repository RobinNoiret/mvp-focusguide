# Story 1.11: Optimistic UI with Data Integrity

**Epic:** 1 - Foundation & Today Page (Standalone Daily Task Management)
**Story Number:** 1.11
**Status:** Draft

---

## Story

**As a** user,
**I want** the app to feel instant and never lose my changes,
**so that** I trust the app with my important tasks.

---

## Acceptance Criteria

1. All mutations update UI immediately
2. Failed requests queued in localStorage with exponential backoff (1s, 2s, 4s, 8s, 16s)
3. Retry queue persists across refreshes
4. Visual indicator for pending mutations
5. Toast on failure after retries: "Unable to sync. Retry?"
6. Manual retry button
7. React Query retry logic configured
8. Background sync polls queue every 30s
9. Navigator.onLine detects connectivity, triggers sync
10. Server authoritative: roll back on rejection
11. Conflict resolution: remove deleted tasks
12. Unit tests simulate failures
13. Integration tests verify data integrity

### Task 2: Implement Mutation Queue in LocalStorage (AC: 2, 3)

- [ ] Create `MutationQueue` service in `apps/web/src/services/mutationQueue.ts`:
  ```typescript
  interface QueuedMutation {
    id: string // Unique ID for this mutation
    type: 'create' | 'update' | 'delete'
    endpoint: string // e.g., '/tasks' or '/tasks/123'
    data: any // Request payload
    attemptCount: number
    lastAttempt: string // ISO timestamp
    createdAt: string // ISO timestamp
  }

  class MutationQueue {
    private readonly STORAGE_KEY = 'mutation-queue'

    // Get all queued mutations
    getQueue(): QueuedMutation[] {
      const queue = localStorage.getItem(this.STORAGE_KEY)
      return queue ? JSON.parse(queue) : []
    }

    // Add mutation to queue
    enqueue(mutation: Omit<QueuedMutation, 'id' | 'attemptCount' | 'createdAt' | 'lastAttempt'>) {
      const queue = this.getQueue()
      const newMutation: QueuedMutation = {
        ...mutation,
        id: `${Date.now()}-${Math.random()}`,
        attemptCount: 0,
        lastAttempt: new Date().toISOString(),
        createdAt: new Date().toISOString(),
      }
      queue.push(newMutation)
      this.saveQueue(queue)
      return newMutation.id
    }

    // Remove mutation from queue (after success)
    dequeue(id: string) {
      const queue = this.getQueue().filter(m => m.id !== id)
      this.saveQueue(queue)
    }

    // Update attempt count
    incrementAttempt(id: string) {
      const queue = this.getQueue()
      const mutation = queue.find(m => m.id === id)
      if (mutation) {
        mutation.attemptCount++
        mutation.lastAttempt = new Date().toISOString()
        this.saveQueue(queue)
      }
    }

    // Clear entire queue
    clear() {
      localStorage.removeItem(this.STORAGE_KEY)
    }

    private saveQueue(queue: QueuedMutation[]) {
      localStorage.setItem(this.STORAGE_KEY, JSON.stringify(queue))
    }
  }

  export const mutationQueue = new MutationQueue()
  ```
- [ ] Queue persists across refreshes (AC 3):
  - Uses localStorage (survives page reload, browser close)
  - JSON serialization for complex data
  - Atomic writes (no partial writes)

  ```typescript
    const queryClient = useQueryClient()

    return useMutation({
      mutationFn: (input: CreateTaskInput) => taskService.createTask(input),

      onMutate: async (newTask) => {
        // AC 1: Optimistic update (immediate UI update)
        await queryClient.cancelQueries({ queryKey: ['today', 'tasks'] })

        const optimisticTask: Task = {
          id: `temp-${Date.now()}`,
          // ... other fields
        }

          [optimisticTask, ...(old || [])]
        )

        return { previousTasks, optimisticTask }
      },

      onError: async (err, variables, context) => {
        // AC 2: Queue mutation on failure
        if (isNetworkError(err) || isServerError(err)) {
          mutationQueue.enqueue({
            type: 'create',
            endpoint: '/tasks',
            data: variables,
          })

          // Don't rollback immediately - keep optimistic update
          // Show pending indicator instead
          toast.info('Saving... Will retry automatically.')
        } else {
          // Validation error or client error: rollback
          queryClient.setQueryData(['today', 'tasks'], context?.previousTasks)
          toast.error('Invalid data. Please try again.')
        }
      },

      onSuccess: (data, variables, context) => {
        // Replace optimistic task with real task from server
        queryClient.invalidateQueries({ queryKey: ['today', 'tasks'] })
      },
    })
  }
  ```

### Task 4: Background Sync Worker (AC: 8, 9)

- [ ] Create background sync service in `apps/web/src/services/backgroundSync.ts`:
  ```typescript
  class BackgroundSync {
    private intervalId: NodeJS.Timeout | null = null
    private readonly SYNC_INTERVAL = 30000 // 30 seconds (AC 8)

    start() {
      // Poll every 30 seconds
      this.intervalId = setInterval(() => {
        this.processQueue()
      }, this.SYNC_INTERVAL)

      // Also process on network reconnect (AC 9)
      window.addEventListener('online', () => {
        console.log('Network reconnected, processing queue')
        this.processQueue()
      })
    }

    stop() {
      if (this.intervalId) {
        clearInterval(this.intervalId)
        this.intervalId = null
      }
    }

    async processQueue() {
      // AC 9: Check connectivity
      if (!navigator.onLine) {
        console.log('Offline, skipping queue processing')
        return
      }

      const queue = mutationQueue.getQueue()

      for (const mutation of queue) {
        // AC 2: Exponential backoff
        const backoff = this.calculateBackoff(mutation.attemptCount)
        const timeSinceLastAttempt = Date.now() - new Date(mutation.lastAttempt).getTime()

        if (timeSinceLastAttempt < backoff) {
          console.log(`Skipping ${mutation.id}, waiting ${backoff - timeSinceLastAttempt}ms`)
          continue
        }

        // Max 5 attempts, then give up
        if (mutation.attemptCount >= 5) {
          console.error(`Mutation ${mutation.id} failed after 5 attempts, removing from queue`)
          mutationQueue.dequeue(mutation.id)
          // AC 5: Show toast for permanent failure
          toast.error('Unable to sync. Some changes may be lost.', {
            action: {
              label: 'Retry',
              onClick: () => this.retryMutation(mutation.id),
            },
          })
          continue
        }

        try {
          await this.executeMutation(mutation)
          mutationQueue.dequeue(mutation.id)
          console.log(`Mutation ${mutation.id} succeeded`)
        } catch (err) {
          mutationQueue.incrementAttempt(mutation.id)
          console.error(`Mutation ${mutation.id} failed, attempt ${mutation.attemptCount + 1}`)
        }
      }
    }

    // AC 2: Exponential backoff - 1s, 2s, 4s, 8s, 16s
    private calculateBackoff(attemptCount: number): number {
      return Math.min(1000 * 2 ** attemptCount, 16000)
    }

    private async executeMutation(mutation: QueuedMutation) {
      const { type, endpoint, data } = mutation

      switch (type) {
        case 'create':
          return await apiClient.post(endpoint, data)
        case 'update':
          return await apiClient.patch(endpoint, data)
        case 'delete':
          return await apiClient.delete(endpoint)
      }
    }

    async retryMutation(id: string) {
      const queue = mutationQueue.getQueue()
      const mutation = queue.find(m => m.id === id)
      if (mutation) {
        try {
          await this.executeMutation(mutation)
          mutationQueue.dequeue(id)
          toast.success('Changes synced successfully')
        } catch (err) {
          toast.error('Retry failed. Please try again.')
        }
      }
    }
  }

  export const backgroundSync = new BackgroundSync()
  ```

### Task 11: Exponential Backoff Implementation (AC: 2)

- [ ] Implement exponential backoff formula (AC 2):
  ```typescript
  const calculateBackoff = (attemptCount: number): number => {
    // 2^n seconds in milliseconds
    // 0: 1s, 1: 2s, 2: 4s, 3: 8s, 4: 16s
    const delay = 1000 * Math.pow(2, attemptCount)
    const maxDelay = 16000 // 16 seconds max (AC 2)
  ```

## Dev Notes

### Why Data Integrity is Critical

[Source: docs/prd.md#NFR1]

**NFR1:** "The system MUST never lose user modifications - all data changes must be persisted with retry mechanisms"

**Why this matters:**
- Users trust apps with important data (their tasks)
- Losing a task = losing user's trust
- Competitors (Todoist, Things) have rock-solid sync
- Users expect "it just works" - silent failures unacceptable

**Story 1.11 implements this guarantee:**
- Optimistic UI: Changes appear instant
- Retry queue: Failed requests automatically retried
- Persistence: Queue survives page reloads
- Manual retry: User can force sync
- Conflict resolution: Server authority prevents data corruption

**User experience:**
App feels instant (optimistic) while guaranteeing data safety (queue + retry).

### Optimistic Updates Trade-offs

**Benefits:**
- ✅ App feels instant (no waiting for server)
- ✅ Users trust the app (changes always visible)
- ✅ Works offline (queue changes, sync later)

**Costs:**
- ❌ More complex code (rollback logic, queue management)
- ❌ Potential conflicts (server state != client state)
- ❌ Storage overhead (localStorage queue)

**For Focus Guide:** Benefits outweigh costs. Data integrity is #1 priority.

### Exponential Backoff Explained

[Source: docs/prd.md#AC 2]

**What is exponential backoff?**
Wait longer between each retry attempt: 1s, 2s, 4s, 8s, 16s.

**Formula:**
```
delay = min(1000 * 2^attemptCount, 16000)
```

**Example:**
- Attempt 0 (first try): Immediate
- Attempt 1 (1st retry): Wait 1s
- Attempt 2 (2nd retry): Wait 2s
- Attempt 3 (3rd retry): Wait 4s
- Attempt 4 (4th retry): Wait 8s
- Attempt 5 (5th retry): Wait 16s (max)

**Why exponential?**
- Early retries: Quick (might be temporary glitch)
- Later retries: Slower (server likely down, don't hammer it)
- Reduces load on failing servers
- Industry standard (AWS, Google Cloud, etc.)

**Why cap at 16s?**
- Don't wait too long (user might close tab)
- Balance retries with user experience
- After 5 failures (31 seconds total), give up and ask user

### localStorage vs IndexedDB for Queue

**localStorage (chosen for MVP):**
- ✅ Simple API (getItem, setItem)
- ✅ Synchronous (no async complexity)
- ✅ ~5-10MB storage (sufficient for queue)
- ✅ Survives page reloads
- ❌ Limited storage (~5MB in some browsers)
- ❌ Blocks main thread (writes are sync)

**IndexedDB (future enhancement):**
- ✅ Large storage (>50MB, no practical limit)
- ✅ Async (doesn't block main thread)
- ✅ Transactional (ACID guarantees)
- ❌ Complex API (harder to use)
- ❌ Overkill for small queue

**Decision:** Use localStorage for MVP. If queue grows large (>100 items), migrate to IndexedDB.

### Queue Size Limits

**Prevent infinite queue growth:**
- Max queue size: 100 mutations
- If queue exceeds 100: Warn user
  - "Too many pending changes. Please check your connection."
- Oldest mutations evicted first (FIFO)
- Or show "Clear queue" option (dangerous - potential data loss)

**For MVP:** No hard limit. Monitor in analytics, add if needed.

### navigator.onLine Reliability

[Source: MDN Web Docs]

**navigator.onLine issues:**
- ❌ Not 100% reliable
- ❌ Browser might report "online" but no internet (e.g., connected to router but router has no WAN)
- ❌ Doesn't detect slow/unreliable connections
- ✅ Better than nothing (useful hint)

**Use as hint, not source of truth:**
```typescript
if (!navigator.onLine) {
  // Definitely offline, don't try API call
  queueMutation()
  return
}

// Might be online, try API call (will queue if fails)
try {
  await apiCall()
} catch (err) {
  queueMutation()
}
```

**Alternative:** Heartbeat ping
- Periodically ping `/health` endpoint
- If fails: Mark as offline
- More reliable but adds server load
- For MVP: Use navigator.onLine (good enough)

### Background Sync API (Future Enhancement)

[Source: Web Platform Features]

**Service Worker Background Sync:**
- Browser-level sync (works even if tab closed)
- `navigator.serviceWorker.sync.register('sync-queue')`
- Browser retries in background with exponential backoff
- **Perfect for this use case**

**Why not use for MVP?**
- ❌ Requires service worker (added complexity)
- ❌ Not supported in all browsers (Safari limited support)
- ❌ Harder to debug
- ✅ MVP: Use JavaScript interval (simpler, works everywhere)

**Future:** Migrate to Background Sync API for PWA.

### Conflict Resolution Strategies

[Source: Distributed Systems Patterns]

**Last-Write-Wins (MVP approach):**
- Simplest strategy
- Server timestamp determines winner
- Latest update wins
- **Downside:** Can lose concurrent edits
- **Acceptable for:** Single-user apps, low conflict rate

**Operational Transform (OT):**
- Google Docs-style conflict resolution
- Merges concurrent edits intelligently
- **Complex:** Requires OT algorithm implementation
- **Overkill for:** MVP task manager

**Conflict-free Replicated Data Types (CRDTs):**
- Data structures that merge automatically
- No conflicts by design
- **Complex:** Requires CRDT library, server changes
- **Future:** Consider for multi-user collaboration

**For Focus Guide MVP:**
Last-Write-Wins is sufficient. Single-user app, conflicts rare.

### Server Authority Principle

[Source: docs/prd.md#AC 10]

**Server is source of truth:**
- Client shows optimistic updates (for UX)
- Server validates and persists
- If server rejects: Client rolls back
- If server modifies: Client adopts server version

**Example: Title exceeds max length**
- Client shows updated title (optimistic)
- Server rejects (400 Bad Request: "Title too long")
- Client reverts to original title
- User sees error toast

**Example: Task deleted by another user**
- User A deletes task
- User B tries to edit same task (optimistic update)
- Server returns 404 Not Found
- Client removes task from cache
- User B sees toast: "Task was deleted"

**Never trust client alone:**
- Client can be tampered with
- Client validation can be bypassed
- Server MUST validate all mutations

### Idempotency Keys (Advanced)

**Problem:**
Request sent to server, server processes, response lost (network error). Client retries. Server processes again. Duplicate task created.

**Solution: Idempotency keys**
```
POST /v1/tasks
Idempotency-Key: temp-1673456789123
```

Server logic:
```typescript
const key = request.header('Idempotency-Key')
const existing = await redis.get(`idempotency:${key}`)
if (existing) {
  return JSON.parse(existing) // Return cached response
}

const task = await Task.create(data)
await redis.setex(`idempotency:${key}`, 86400, JSON.stringify(task)) // 24h
return task
```

**Benefits:**
- Prevents duplicate creates on retry
- Safe to retry any number of times
- Industry standard (Stripe, Twilio, etc.)

**For MVP:** Skip (low priority). Add if duplicate tasks become issue.

### User Communication Best Practices

**Don't scare users:**
❌ "Mutation queue processing failed"
✅ "Saving your changes..."

❌ "Network error 500 from server"
✅ "Unable to save. We'll keep trying."

❌ "ECONNREFUSED localhost:3333"
✅ "Connection issue. Changes saved locally."

**Reassure users:**
- "Your changes are safe"
- "Will sync automatically"
- "You can keep working offline"

**Be actionable:**
- Provide retry button
- Explain what to do ("Check your internet connection")
- Link to help docs

### Performance Considerations

**Queue processing overhead:**
- Polling every 30s: Minimal CPU
- Processing queue: Only on changes
- localStorage reads: Fast (cached)

**Optimization:**
- Batch API calls (send multiple mutations in one request)
- Debounce rapid mutations (e.g., typing in title)
- Lazy queue initialization (only if mutations fail)

**For MVP:** No optimization needed. Queue size will be small (<10 items).

### Privacy & Data Retention

**LocalStorage data:**
- Contains user's task data
- Persists until explicitly cleared
- Survives browser updates, OS restarts

**Security:**
- localStorage not encrypted
- Visible to malware/extensions
- Acceptable for non-sensitive task data

**User control:**
- Provide "Clear offline data" button in settings
- Clears mutation queue and cached data
- Warning: "Pending changes will be lost"

**GDPR compliance:**
- LocalStorage is client-side (not server storage)
- User can clear via browser settings
- Include in privacy policy
