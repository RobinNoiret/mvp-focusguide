### Task 5: CORS Configuration (AC: 11)

- [ ] Configure CORS in AdonisJS `config/cors.ts` (AC 11):
  ```typescript
  import { defineConfig } from '@adonisjs/cors'
  import env from '#start/env'

  export default defineConfig({
    enabled: true,
    origin: (origin) => {
      // Allow frontend domains
      const allowedOrigins = [
        'https://focusguide.app',
        'https://app.focusguide.app',
        'https://*.vercel.app', // Preview deployments
      ]

      // Allow localhost in development
      if (env.get('NODE_ENV') === 'development') {
        allowedOrigins.push('http://localhost:3000')
      }

      // Check if origin is allowed
      return allowedOrigins.some(allowed => {
        if (allowed.includes('*')) {
          const regex = new RegExp(allowed.replace('*', '.*'))
          return regex.test(origin)
        }
        return origin === allowed
      })
    },
    methods: ['GET', 'HEAD', 'POST', 'PUT', 'PATCH', 'DELETE'],
    headers: true,
    credentials: true,
    maxAge: 86400, // 24 hours
  })
  ```

### Database Migration Strategy

[Source: docs/prd.md#AC 5]

**Why run migrations on deployment?**
- Ensures database schema matches code
- Prevents "migration drift" between environments
- Automated (no manual steps)

**Migration workflow:**
1. Push code to main
2. Railway builds app
3. **Migrations run:** `node ace migration:run --force`
4. App starts with correct schema
5. If migration fails: Deployment aborted (safe)

**Migration best practices:**
- Always test migrations locally first
- Never modify existing migrations (create new ones)
- Use transactions (automatic rollback on error)
- Keep migrations small and focused

**Rollback strategy:**
If migration causes issue:
- Railway: Rollback to previous deployment (1 click)
- Database: Manually rollback migration (`migration:rollback`)
- Or: Create new migration to undo changes

### CORS Configuration Explained

[Source: docs/prd.md#AC 11]

**What is CORS?**
Browser security mechanism preventing cross-origin requests.

**Problem without CORS:**
```
Frontend: https://focusguide.app
API: https://api.focusguide.app
Browser: ❌ Blocked (different origin)
```

**Solution: CORS headers**
API sends header:
```
Access-Control-Allow-Origin: https://focusguide.app
Access-Control-Allow-Credentials: true
```

**Our CORS config:**
- Allow production: `focusguide.app`
- Allow preview deployments: `*.vercel.app`
- Allow localhost (dev only): `localhost:3000`
- Block everything else

**Wildcard CORS (dangerous):**
```typescript
origin: '*' // ❌ NEVER DO THIS
```
Allows any website to call your API. Security risk!

**Credentials:**
```typescript
credentials: true
```
Allows cookies/auth headers. Required for JWT tokens.

### Sentry Error Tracking Value

[Source: docs/prd.md#NFR16]

**Why Sentry?**
- Know when things break (before users report)
- Stack traces show exact error location
- Breadcrumbs show user actions leading to error
- Alerts via email/Slack

**Sentry captures:**
- JavaScript errors (frontend)
- API errors (backend)
- Unhandled promise rejections
- Console errors (optional)

**Sentry workflow:**
1. Error occurs in production
2. Sentry captures error
3. Email alert sent to team
4. Developer investigates in Sentry dashboard
5. Fix deployed
6. Sentry shows error resolved

**Privacy:**
Sentry doesn't capture:
- Passwords (auto-scrubbed)
- Credit cards (auto-scrubbed)
- User data (unless explicitly sent)

**Free tier limits:**
- 5,000 events/month
- Sufficient for MVP
- Upgrade if exceeds

  "uptime": 12345.67,
  "checks": {
    "database": "ok",
    "redis": "ok"
  }

**Used for:**
- **Uptime monitoring:** UptimeRobot pings every 5 min
- **Load balancer health:** Railway checks before routing
- **Debugging:** Quick status check

**Status codes:**
- 200 OK: All systems operational
- 503 Service Unavailable: Database or Redis down

**What to check:**
- ✅ Database connection (SELECT 1)
- ✅ Redis connection (PING)
- ✅ Server uptime
- ❌ Don't check: External APIs (slow, unreliable)

### CI/CD Pipeline Benefits

[Source: docs/prd.md#NFR18]

**CI/CD = Continuous Integration / Continuous Deployment**

**Benefits:**
- Catch bugs before production (automated tests)
- Prevent broken main branch (PR checks)
- Faster deployments (automated)
- Confidence to ship often

**Our pipeline:**
1. Developer creates PR
2. GitHub Actions runs: lint, type-check, test, build
3. Vercel creates preview deployment
4. Reviewer checks tests pass + preview looks good
5. PR merged to main
6. Vercel + Railway auto-deploy production
7. Users see changes in ~2 minutes

**Without CI/CD:**
- Manual testing (slow, error-prone)
- Manual deployment (risky)
- Broken production deploys
- Fear of shipping changes

### Vercel Preview Deployments

[Source: docs/prd.md#AC 8]

**What are preview deployments?**
Temporary URL for each PR to test changes before merge.

**Workflow:**
1. Create PR
2. Vercel auto-builds
3. Unique URL: `focus-guide-pr-42.vercel.app`
4. Reviewer clicks URL, tests changes
5. Approve PR
6. Merge → Production

**Benefits:**
- Test UI changes visually
- Share with stakeholders (before merge)
- Catch visual regressions
- Safe testing (doesn't affect production)

**Preview limitations:**
- Uses production API (shared database)
- Alternative: Deploy preview API too (complex, overkill for MVP)

### Rollback Strategy

**Instant rollback (both platforms):**

**Vercel:**
1. Deployments → View all
2. Find last working deployment
3. Click "Promote to Production"
4. Done (instant)

**Railway:**
1. Deployments → View history
2. Find last working deployment
3. Click "Rollback to this deployment"
4. Done (instant)

**Database rollback (harder):**
- Can't rollback migrations automatically
- Options:
  1. Create new migration to undo changes
  2. Restore database backup (Railway auto-backups)
  3. Manually revert via SQL

**Prevention > Rollback:**
- Test thoroughly before merge
- Use preview deployments
- Run migrations in staging first
