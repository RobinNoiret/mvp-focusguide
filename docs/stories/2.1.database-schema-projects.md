# Story 2.1: Database Schema for Projects

**Epic:** 2 - Projects Management (Strategic Planning Layer)
**Story Number:** 2.1
**Status:** Ready for Review

---

## Story

**As a** developer,
**I want** a database schema for projects and task-project relationships,
**so that** users can organize tasks into projects.

---

## Acceptance Criteria

1. Migration for projects table: id, user_id (FK), title, description, deadline, tags (array), timestamps, deleted_at
2. tasks.project_id references projects.id (nullable)
3. Check constraint: project_id NOT NULL → project_status NOT NULL
4. Check constraint: project_id NULL → project_status NULL
5. Indexes: projects.user_id, projects.deleted_at, tasks.project_id
6. Project model with hasMany(Task), belongsTo(User)
7. Task model with belongsTo(Project)
8. Migration rollback logic
9. Seeders for development
10. Migrations run on dev, staging, production

### Task 3: Create Project Model (AC: 6, 7)

- [x] Generate Project model:

- [x] Implement Project model (AC 6):
  ```typescript
  import { DateTime } from 'luxon'
  import { BaseModel, column, belongsTo, hasMany, BelongsTo, HasMany } from '@adonisjs/lucid/orm'
  import User from '#models/user'
  import Task from '#models/task'

  export default class Project extends BaseModel {
    @column({ isPrimary: true })
    declare id: string

    @column()
    declare userId: string

    @column()
    declare title: string

    @column()
    declare description: string | null

    @column.date()
    declare deadline: DateTime | null

    @column({
      prepare: (value: string[]) => JSON.stringify(value), // Array to JSON for storage
      consume: (value: string) => JSON.parse(value), // JSON to Array on read
    })
    declare tags: string[]

    @column.dateTime({ autoCreate: true })
    declare createdAt: DateTime

    @column.dateTime({ autoCreate: true, autoUpdate: true })
    declare updatedAt: DateTime

    @column.dateTime()
    declare deletedAt: DateTime | null

    // Relationships (AC 6)
    @belongsTo(() => User)
    declare user: BelongsTo<typeof User>

    @hasMany(() => Task)
    declare tasks: HasMany<typeof Task>

    // Soft delete helper
    get isDeleted(): boolean {
      return this.deletedAt !== null
    }

    // Computed property: completion percentage
    async getCompletionPercentage(): Promise<number> {
      const tasks = await this.related('tasks').query().whereNull('deleted_at')
      if (tasks.length === 0) return 0

      const doneTasks = tasks.filter(task => task.projectStatus === 'done')
      return Math.round((doneTasks.length / tasks.length) * 100)
    }
  }
  ```

## Dev Notes

### Project Status vs Today Status

**Two separate status enums:**

**Today Status (from Epic 1):**
- `'backlog'` - Planned but not for today
- `'todo_today'` - Scheduled for today
- `'in_progress'` - Currently working on
- `'done'` - Completed

**Project Status (new in Epic 2):**
- `'backlog'` - Planned for project
- `'todo'` - Ready to work on (note: different from `'todo_today'`)
- `'in_progress'` - In progress within project
- `'done'` - Completed

**Why different?**
- Project: Strategic planning ("what needs to be done")
- Today: Daily execution ("what I'm doing today")
- A task can be `project_status='todo'` but `today_status='in_progress'`
- Example: Task is "ready to work on" in project, but actively being worked on today

**Both nullable:**
- `today_status = null` → Task not in Today board
- `project_status = null` → Task is standalone (no project)

### Check Constraints Rationale

**Check constraint (AC 3, 4):**
```sql
(project_id IS NULL AND project_status IS NULL) OR
(project_id IS NOT NULL AND project_status IS NOT NULL)
```

**Why needed?**
Enforces data integrity: A task either:
1. Belongs to a project (has project_id AND project_status), OR
2. Is standalone (no project_id, no project_status)

**Invalid states prevented:**
- ❌ `project_id = uuid, project_status = null` (project without status)
- ❌ `project_id = null, project_status = 'todo'` (status without project)

**Benefits:**
- Prevents orphaned statuses
- Simplifies queries (don't need to check both fields)
- Clearer data model

### Cascade Delete Strategy

**Foreign key with ON DELETE CASCADE:**
```typescript
table.uuid('project_id')
  .references('id')
  .inTable('projects')
  .onDelete('CASCADE')
```

**Behavior:**
- Soft delete project (set deleted_at): Tasks NOT cascade deleted
- Hard delete project (actual DELETE): Tasks cascade deleted

**Why this design?**
- Soft delete (app default): Preserves tasks for data integrity
- Hard delete (admin only): Removes orphaned tasks from DB
- User story (Epic 2.7): Deleting project cascades to tasks

**Implementation:**
Story 2.7 will soft delete project AND soft delete all its tasks in application logic (not DB cascade).

### PostgreSQL Array Type for Tags

**Why PostgreSQL array?**
```typescript
table.specificType('tags', 'text[]')
```

**Advantages:**
- ✅ Native PostgreSQL support (fast queries)
- ✅ No junction table needed (simpler schema)
- ✅ Easy to query: `WHERE 'Marketing' = ANY(tags)`
- ✅ Type-safe with Lucid ORM

**Disadvantages:**
- ❌ Not normalized (can't enforce tag uniqueness across projects)
- ❌ Hard to rename tags globally
- ❌ Limited to PostgreSQL (not portable to MySQL)

**For MVP:**
Array is sufficient. Future: Migrate to tags table if need advanced features (tag management, autocomplete, tag analytics).

**Alternative (normalized):**
```sql
CREATE TABLE tags (id, name);
CREATE TABLE project_tags (project_id, tag_id);
```
More complex but more powerful. Overkill for MVP.

### Indexes Performance Impact

**Indexes added (AC 5):**
- `projects.user_id` - Fast lookup: "Show my projects"
- `projects.deleted_at` - Fast filter: "Exclude deleted projects"
- `tasks.project_id` - Fast lookup: "Show tasks for this project"

**Query performance:**
Without index:
```sql
SELECT * FROM tasks WHERE project_id = 'uuid';
-- Seq Scan (slow, scans all rows)
```

With index:
```sql
SELECT * FROM tasks WHERE project_id = 'uuid';
-- Index Scan (fast, O(log n) lookup)
```

**Trade-off:**
- Faster reads (queries)
- Slower writes (inserts/updates must update index)
- More disk space

For task manager: Reads >> Writes, so indexes are win.

### Computed Property: Completion Percentage

**Why computed, not stored?**
```typescript
async getCompletionPercentage(): Promise<number> {
  const tasks = await this.related('tasks').query()
  const doneTasks = tasks.filter(t => t.projectStatus === 'done')
  return (doneTasks.length / tasks.length) * 100
}
```

**Pros:**
- ✅ Always accurate (real-time calculation)
- ✅ No denormalization (no stale data)
- ✅ Simple (no triggers/observers needed)

**Cons:**
- ❌ Slower (requires query)
- ❌ N+1 query problem if loading many projects

**Solution for N+1:**
```typescript
// Eager load task counts
const projects = await Project.query()
  .withCount('tasks', (query) => {
    query.as('total_tasks')
  })
  .withCount('tasks', (query) => {
    query.where('project_status', 'done').as('done_tasks')
  })

// Calculate in-memory
projects.forEach(p => {
  p.completionPercentage = (p.doneTasks / p.totalTasks) * 100
})
```

For MVP: Computed property is fine (users have <50 projects).

### Soft Delete vs Hard Delete

**Soft delete (app default):**
```typescript
project.deletedAt = DateTime.now()
await project.save()
```
- Sets timestamp, row remains in DB
- Excluded from queries via `whereNull('deleted_at')`
- Recoverable (future feature: restore)

**Hard delete (dangerous):**
```typescript
await project.delete()
```
- Physically removes row from DB
- Cascade deletes tasks (foreign key ON DELETE CASCADE)
- Irreversible
- Only for admin cleanup (not exposed to users)

**For MVP:**
Only soft delete exposed to users. Data safety first.
