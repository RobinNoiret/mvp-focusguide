## Acceptance Criteria

1. GET /v1/projects returns all non-deleted projects with completionPercentage, taskCounts
2. POST /v1/projects creates project (title, description, deadline, tags)
3. GET /v1/projects/:id returns project with tasks grouped by project_status
4. PATCH /v1/projects/:id updates metadata
5. DELETE /v1/projects/:id soft deletes project and cascade deletes tasks
6. All endpoints validate user ownership
7. Input validation: title max 200, description max 2000, tags max 10, deadline future
8. Completion percentage: 0% if no tasks, else (done/total * 100)
9. Task counts grouped by project_status
10. Unit tests for all endpoints
11. Integration tests verify cascade delete

### Task 2: Implement GET /v1/projects (AC: 1, 8, 9)

- [ ] Implement `index` method (AC 1):
  ```typescript
  async index({ auth, response }: HttpContext) {
    // Fetch all non-deleted projects for authenticated user
    const projects = await Project.query()
      .where('user_id', auth.user!.id)
      .whereNull('deleted_at')
      .orderBy('created_at', 'desc')

    // Calculate stats for each project (AC 8, 9)
    const projectsWithStats = await Promise.all(
      projects.map(async (project) => {
        const tasks = await project.related('tasks')
          .query()
          .whereNull('deleted_at')

        const totalTasks = tasks.length
        const doneTasks = tasks.filter(t => t.projectStatus === 'done').length

        // AC 8: Completion percentage
        const completionPercentage = totalTasks === 0
          ? 0
          : Math.round((doneTasks / totalTasks) * 100)

        // AC 9: Task counts by status
        const taskCounts = {
          backlog: tasks.filter(t => t.projectStatus === 'backlog').length,
          todo: tasks.filter(t => t.projectStatus === 'todo').length,
          in_progress: tasks.filter(t => t.projectStatus === 'in_progress').length,
          done: doneTasks,
        }

        return {
          ...project.serialize(),
          completion_percentage: completionPercentage,
          task_count: totalTasks,
          task_counts: taskCounts,
        }
      })
    )

    return response.ok(projectsWithStats)
  }
  ```

  async destroy({ auth, params, response }: HttpContext) {
    // Fetch project with ownership validation (AC 6)
    const project = await Project.query()
      .where('id', params.id)
      .where('user_id', auth.user!.id)
      .whereNull('deleted_at')

    await project.save()

  }

## Dev Notes

### RESTful API Design

**Standard REST endpoints:**
- `GET /v1/projects` - List all (index)
- `POST /v1/projects` - Create new (store)
- `GET /v1/projects/:id` - Get one (show)
- `PATCH /v1/projects/:id` - Update (update)
- `DELETE /v1/projects/:id` - Delete (destroy)

**HTTP Methods:**
- GET: Read, idempotent, no body
- POST: Create, not idempotent, has body
- PATCH: Partial update, idempotent, has body
- DELETE: Remove, idempotent, no body

**HTTP Status Codes:**
- 200 OK: GET, PATCH successful
- 201 Created: POST successful
- 204 No Content: DELETE successful
- 400 Bad Request: Validation error
- 401 Unauthorized: Not authenticated
- 404 Not Found: Resource not found
- 500 Internal Server Error: Unexpected error

### Completion Percentage Formula

[Source: docs/prd.md#AC 8]

**Formula:**
```typescript
completionPercentage = totalTasks === 0
  ? 0
  : Math.round((doneTasks / totalTasks) * 100)
```

**Examples:**
- 0 tasks → 0%
- 5/10 tasks done → 50%
- 1/3 tasks done → 33% (rounded)
- 10/10 tasks done → 100%

**Why round?**
- UI shows whole numbers (no "33.33%")
- Cleaner display
- Acceptable precision loss

**Edge case: 0 tasks**
- Return 0%, not null/undefined
- Consistent type (always number)
- Logical: No tasks = no progress

### Task Counts Grouping

[Source: docs/prd.md#AC 9]

**Why group by status?**
Frontend displays:
- "5 backlog, 8 todo, 2 in progress, 9 done"
- Progress bars per status
- Filtering by status

**Data structure:**
```typescript
task_counts: {
  backlog: 5,
  todo: 8,
  in_progress: 2,
  done: 9
}
```

**Alternative (not used):**
```typescript
tasks: [
  { id, title, status: 'todo' },
  // ... all tasks
]
```
Heavy (sends all task data). We only need counts for project list.

**When to send full tasks:**
`GET /v1/projects/:id` sends grouped tasks (needed for detail view).

### Ownership Validation Security

[Source: docs/prd.md#AC 6]

**Critical security requirement:**
Users can ONLY access their own projects.

**Implementation:**
```typescript
.where('user_id', auth.user!.id)
```

**Why 404, not 403?**
```typescript
// BAD: Reveals project exists
if (project.userId !== auth.user.id) {
  return response.forbidden() // 403
}

// GOOD: Same response for both cases
.where('id', params.id)
.where('user_id', auth.user!.id)
.firstOrFail() // 404 if either condition fails
```

**Attack prevented:**
Attacker can't enumerate other users' projects by trying UUIDs.

### Input Validation Strategy

[Source: docs/prd.md#AC 7]

**Why validate on backend?**
- Client validation can be bypassed
- Security: Never trust client
- Data integrity: Garbage in = garbage out

**Validation rules:**
- Title: 1-200 chars (after trim)
- Description: 0-2000 chars
- Tags: Max 10 tags, each max 50 chars
- Deadline: Must be future date

**VineJS advantages:**
- Type-safe validators
- Auto-infers TypeScript types
- Clear error messages
- Composable rules

**Example error:**
```json
{
  "errors": [{
    "field": "title",
    "rule": "maxLength",
    "message": "The title field must not be greater than 200 characters",
    "meta": { "max": 200 }
  }]
}
```

### Cascade Delete Implementation

[Source: docs/prd.md#AC 5 + Story 2.7]

**Two levels of cascade:**

**1. Soft delete (app logic):**
```typescript
// Delete project
project.deletedAt = DateTime.now()
await project.save()

// Cascade to tasks
await project.related('tasks')
  .query()
  .update({ deleted_at: DateTime.now() })
```

**2. Hard delete (database FK):**
```sql
-- Foreign key constraint
ON DELETE CASCADE
```

If project physically deleted from DB, tasks also deleted.

**Why both?**
- App uses soft delete (data safety)
- Database cascade is safety net (prevents orphaned tasks)
- Consistency: Tasks can't exist without project

### N+1 Query Problem

**Problem:**
```typescript
const projects = await Project.query().where('user_id', userId)

// N+1: Queries each project's tasks separately
for (const project of projects) {
  const tasks = await project.related('tasks').query() // N queries
}
```

**Solution: Eager loading**
```typescript
const projects = await Project.query()
  .where('user_id', userId)
  .preload('tasks') // 1 query for all tasks

// No additional queries needed
for (const project of projects) {
  const tasks = project.tasks // Already loaded
}
```

**Performance:**
- N+1: 1 + N queries (slow with many projects)
- Eager loading: 2 queries total (fast)

### Deadline Validation

**Why validate deadline is future?**
Past deadlines don't make sense for new projects.

**Implementation:**
```typescript
if (data.deadline && data.deadline < DateTime.now()) {
  return response.badRequest({ error: 'Deadline must be in the future' })
}
```

**Edge cases:**
- Today's date: Valid (future enough)
- Past date: Invalid
- No deadline: Valid (optional field)
- Far future (year 3000): Valid (no max limit)

**Update vs Create:**
- Create: Must be future
- Update: Can keep past deadline (already set)
- Or: Allow updating to past (flexible)

Decision for MVP: Validate future on both create and update.

### Tags Array Handling

**PostgreSQL array:**
```sql
tags text[] DEFAULT '{}'
```

**JSON serialization:**
```typescript
@column({
  prepare: (value: string[]) => JSON.stringify(value),
  consume: (value: string) => JSON.parse(value),
})
declare tags: string[]
```

**Why this is needed:**
Lucid ORM doesn't natively handle PostgreSQL arrays. We serialize to JSON string for storage, deserialize on read.

**Alternative:**
Use PostgreSQL-specific package for native array support. Overkill for MVP.

### HTTP Method Semantics

**PATCH vs PUT:**
- PATCH: Partial update (update some fields)
- PUT: Full replacement (replace entire resource)

**We use PATCH because:**
- Can update just title, leave description unchanged
- More flexible
- Industry standard for partial updates

**Idempotency:**
- PATCH: Idempotent (same request twice = same result)
- POST: Not idempotent (creates duplicate)
- DELETE: Idempotent (delete twice = still deleted)
