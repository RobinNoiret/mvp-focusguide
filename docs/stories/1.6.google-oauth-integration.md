# Story 1.6: Google OAuth Integration

**Epic:** 1 - Foundation & Today Page (Standalone Daily Task Management)
**Story Number:** 1.6
**Status:** Draft

---

## Story

**As a** user,
**I want** to log in using my Google account,
**so that** I can access the app quickly without creating a password.

---

## Acceptance Criteria

1. Google OAuth configured in AdonisJS (client ID, secret)
2. GET /v1/auth/google/redirect redirects to Google consent
3. GET /v1/auth/google/callback handles callback, exchanges tokens
4. If user exists, log in; if not, create user with email_verified: true
5. Google login button on /login with icon
6. Successful OAuth redirects to Today page
7. Error handling for OAuth failures
8. User profile includes OAuth provider indicator
9. OAuth provider stored in database
10. Integration test with mock Google API

## Dev Notes

### OAuth 2.0 Flow Overview

[Source: docs/architecture.md#Authentication Strategy]

Focus Guide implements the **Authorization Code Flow** (most secure for web apps):

**Flow Steps:**
1. User clicks "Continue with Google" on login page
2. Frontend redirects to backend `/v1/auth/google/redirect`
3. Backend redirects to Google consent screen with client_id, redirect_uri, state
4. User approves consent
5. Google redirects back to backend `/v1/auth/google/callback?code=xxx&state=xxx`
6. Backend exchanges code for access token (server-to-server)
7. Backend fetches user profile from Google API
8. Backend creates/updates user, generates JWT tokens
9. Backend redirects to frontend `/auth/callback?access_token=xxx&refresh_token=xxx`
10. Frontend stores tokens, redirects to `/today`

**Why this flow?**
- Client secret never exposed to frontend
- Authorization code can only be exchanged once
- State parameter prevents CSRF attacks

### Google OAuth Scopes

[Source: docs/prd.md#Story 1.6 AC 2]

**Required Scopes:**
- `openid` - OpenID Connect authentication
- `email` - User's email address
- `profile` - User's basic profile info (name, picture)

**Scope Configuration:**
```typescript
// In @adonisjs/ally config

```

These are minimal scopes for authentication. Additional scopes (calendar, drive) would require app verification by Google.

### AdonisJS Ally Package

[Source: docs/architecture.md#Tech Stack + Authentication]

**Why @adonisjs/ally?**
- Official AdonisJS social authentication package
- Built-in support for Google, GitHub, Facebook, Twitter
- Handles OAuth flow complexity (state, PKCE, token exchange)
- Type-safe configuration
- Easy to extend with custom providers


**Configuration file:** `config/ally.ts`

### User Creation vs Login Logic (AC 4)

[Source: docs/prd.md#Story 1.6 AC 4]

**Decision Tree:**
```
User with email exists?
├─ YES → Is oauth_provider 'google' or null?
│  ├─ YES → Log in existing user (update avatar, provider_id)
│  └─ NO (is 'email') → ERROR: "Email already registered with password"
└─ NO → Create new user with email_verified: true
```

**Why email_verified: true for OAuth users?**
Google has already verified the email during their OAuth process. We trust Google's verification.

**Why prevent OAuth if email registered with password?**
Security: Prevents account takeover if attacker gains access to victim's Google account. User should log in with password and optionally link Google later (future feature).

### State Parameter for CSRF Protection

[Source: Security Best Practices]

**What is the state parameter?**
A random token generated by our server, included in OAuth authorization URL, and validated when user returns from Google.

**Why is it needed?**
Prevents CSRF attacks where attacker tricks victim into authorizing attacker's Google account to victim's app account.

**Implementation:**
```typescript
// In /redirect endpoint
const state = crypto.randomBytes(32).toString('hex')
await redis.setex(`oauth:state:${state}`, 600, userId || 'anonymous') // 10min expiry
// Include state in Google authorization URL

// In /callback endpoint
const stateFromRedis = await redis.get(`oauth:state:${state}`)
if (!stateFromRedis) throw new Error('Invalid state')
await redis.del(`oauth:state:${state}`) // Single use
```

### Token Transmission Security

[Source: docs/architecture.md#Security Architecture]

**Challenge:** How to pass JWT tokens from backend callback to frontend?

**Options:**

**Option 1: Query Parameters (AC 6 implies this):**
```
/auth/callback?access_token=xxx&refresh_token=xxx
```
- ✅ Simple implementation
- ❌ Tokens visible in URL (browser history, logs)
- ❌ Not recommended for production

**Option 2: Secure httpOnly Cookies (RECOMMENDED):**
```typescript
// Backend sets cookies
response.cookie('access_token', token, { httpOnly: true, secure: true, sameSite: 'strict' })
response.redirect('{FRONTEND_URL}/auth/callback')

// Frontend reads via API call (not JavaScript)
```
- ✅ Secure (not accessible via JavaScript)
- ✅ Automatic CSRF protection with sameSite
- ❌ Slightly more complex

**Option 3: POST to Frontend with Form:**
Backend returns HTML form that auto-submits to frontend with tokens in POST body.
- ✅ Tokens not in URL
- ✅ One-time use
- ❌ Complex implementation

**Recommendation for MVP:** Use Option 1 (query params) but only over HTTPS. Consider Option 2 for production.

### Handling Email Conflicts

[Source: docs/prd.md#Story 1.6 AC 4 + Security Considerations]

**Scenario:** User registered with email/password for `test@example.com`, then tries Google OAuth with same email.

**Security Risk:** If allowed, attacker who compromises victim's Google account could access victim's Focus Guide account.

**Solution:** Prevent OAuth login if email already exists with password auth.

**User Experience:**
- Show error: "This email is already registered. Please log in with your password."
- Provide link to password login
- Future enhancement: Allow account linking (password + OAuth) after password verification

**Database Check:**
```typescript
const user = await User.findBy('email', googleEmail)
if (user && user.oauth_provider === 'email') {
  throw new Error('Email already registered with password')
}
```

### Error Handling Edge Cases

[Source: docs/prd.md#Story 1.6 AC 7]

**Comprehensive Error Scenarios:**

1. **User cancels OAuth:**
   - Google redirects with `?error=access_denied`
   - Show: "Login cancelled. Please try again."

2. **Invalid state (CSRF attack):**
   - Backend detects state mismatch
   - Return 400 Bad Request
   - Frontend shows: "Security error. Please start over."

3. **Google API down/timeout:**
   - Backend catches network error
   - Return 500 Internal Server Error
   - Frontend shows: "Login failed. Please try again later."

4. **User denies email permission:**
   - Google sends limited profile
   - Backend detects missing email
   - Return 400 with message: "Email permission required"

5. **Email not verified on Google:**
   - Google API returns `email_verified: false`
   - Backend rejects login
   - Show: "Please verify your email with Google first"

6. **Expired authorization code:**
   - User takes too long on consent screen
   - Google rejects code exchange
   - Show: "Login expired. Please try again."

### Integration with Existing Auth System

[Source: docs/prd.md#Story 1.2, 1.3]

**JWT Token Generation:**
OAuth users receive same JWT tokens as email/password users (from Story 1.2):
- Access token: 15-minute expiry
- Refresh token: 7-day expiry

**No separate OAuth token system needed.** Google's OAuth is only used for authentication, not authorization of API requests.

**User Model Compatibility:**
OAuth users have all same fields as email/password users except:
- `password`: null (no password hash)
- `oauth_provider`: 'google'
- `oauth_provider_id`: Google user ID
- `email_verified`: always true
